# Radicle transport security gate

Status: 2026-10-30

Sources:

- https://radicle.dev/2026/09/23/disclosure-of-vulnerability-in-network-protocol
- https://radicle.network/nodes/seed.radicle.dev/rad%3Az3gqcJUoA1n9HaHKufZs5FCSGazv5/patches/828581ae87d842dcdc67c3b08bb3bc9d940f3d8f
- Stock Radicle source/compatibility baseline: `1.10.3` (runtime rejected)
- Reviewed delegate-free fork base: `244a8b6fca9ebffe7543cdb2b486a78c7df9cf78`

## Reported issue

Radicle disclosed two network-protocol vulnerabilities affecting all released
versions:

1. application traffic through established Noise sessions was sent in
   plaintext;
2. the peer handshake did not reliably authenticate the claimed Node ID, so a
   peer could impersonate an allow-listed Node ID.

Radicle says signed references still protect repository integrity. The direct
confidentiality risk primarily affects private repositories. Peer impersonation
can expose content intended for a Node ID allowlist and still matters for
public-network abuse, resource use, and authorization boundaries.

Tor, I2P, VPNs, and similar overlays reduce observer exposure but do not repair
the peer-authentication flaw, so they are not treated as a sufficient
workaround.

## Project decision

This forge targets public repositories. While the Radicle node transport gate is
active:

- private repositories are unsupported;
- no private content may be placed in a storage bundle, Idena action, or Idena
  IPFS object;
- the Radicle node, peer sync, fetch, cloning, and seeding paths are disabled;
- the forge uses Radicle only for the local Git storage, issue, patch, review,
  and COB data model;
- Idena actions and signed object bindings establish authorship and governance;
- Idena IPFS is the only content-distribution transport; and
- every accepted storage bundle still has to pass `refs/rad/id`, RID, object,
  and diff verification.

This preserves the Radicle data model without relying on the vulnerable Radicle
network transport. It also fits the project requirement that content and UI
distribution remain inside the Idena ecosystem.

## Runtime enforcement

The forge's Radicle client:

- uses a fail-closed allowlist instead of a network-command blocklist;
- accepts only the exact `cob log`, `cob show`, `patch diff --no-announce`, and
  `patch label idena/merge-request --no-announce` argument forms generated by
  the client;
- rejects every new, unknown, malformed, announcing, node, discovery, clone,
  fetch, sync, seed, and replication command;
- requires an absolute isolated `RAD_HOME`;
- rejects an occupied `network-disabled.sock` path and every active Unix socket
  found directly under `$RAD_HOME/node`;
- requires the exact executable digest through `RAD_BIN_SHA256` or the
  equivalent `Client.ExpectedBinarySHA256` value;
- verifies `rad --version` and accepts only the reviewed `244a8b6` Idena fork;
  stock delegate-bearing, Radicle 2.x, and unknown builds fail closed;
- passes only `PATH`, temporary-directory, locale, and platform runtime values
  to child processes; node API keys, Git overrides, ambient `RAD_*` values,
  and unrelated credentials are excluded. The reviewed Radicle CLI alone also
  receives its explicitly resolved `RAD_PASSPHRASE`;
- pins `RAD_HOME` to the explicitly selected profile; and
- points `RAD_SOCKET` at the verified-absent `network-disabled.sock` path.

The Idena private key is never read by the forge: `dna_sign` runs inside the
local Idena node and returns only a public signature. The forge does not add
the Radicle profile's private-key file to repository bundles, Idena IPFS
objects, actions, or receipts.

The relevant tests are `TestRadicleCommandAllowlist`,
`TestRadicleRunRequiresPinnedSupportedBinaryAndNoNodeSocket`, and
`TestRadicleCommandEnvironmentCannotReachNode`.

## Operator controls

Before running the forge or a first trial:

```sh
export RAD_HOME="/path/to/isolated/radicle-home"
export RAD_SOCKET="$RAD_HOME/node/network-disabled.sock"
export RAD_BIN="/path/to/reviewed/rad"
export RAD_BIN_SHA256="<reviewed-64-hex-digest>"

test ! -S "$RAD_HOME/node/control.sock"
test ! -e "$RAD_HOME/node/network-disabled.sock"
```

`RAD_BIN_SHA256` is a drift guard, not a substitute for review. Do not approve a
new executable by calculating its digest after the fact.

Do not start or connect a Radicle node:

```text
rad node start
rad node connect
rad sync
rad fetch
rad seed
rad clone
```

For every existing private repository in a Radicle profile, stop serving it:

```sh
rad ls --private --all
rad block <RID>
```

Use `rad block` rather than `rad unseed`, because `unseed` can fall back to a
profile-wide `allow` policy. Stopping a node or blocking a repository does not
recover content that was already transmitted. Treat previously networked
private repositories as disclosed and rotate any exposed credentials.

## Radicle 2.0 draft review

The 2026-10-28 draft revision `055f6a08cb936971e897592a0da1e3834ce984e2`
replaces the old transport with iroh and adds useful protections against an
oversized gossip allocation, a non-reading peer blocking the runtime, and a
dead service thread leaving the runtime alive. It is not accepted by this
forge because it is an unmerged draft and its production preset hard-codes
Radicle-operated relay and Pkarr services under `iroh.radicle.network` plus the
`iris.radicle.network` and `rosa.radicle.network` bootstrap nodes. It also
retains upstream delegate and canonical-reference assumptions.

Those services cannot be part of an Idena-only deployment. The eventual port
must use Idena-bound discovery, no Radicle-operated bootstrap or DNS service,
and relay-disabled direct connections for the first trial. It must preserve the
delegate-free identity format and may not make P2P availability an input to the
checkpoint reducer.

## Upgrade gate

Radicle's stated resolution replaces the transport with iroh and is expected to
be a wire-incompatible major release. The secure transport remains disabled
until all of the following are available and independently reviewed:

1. a released Radicle version that documents the transport fixes;
2. tests demonstrating encrypted transport and authenticated peer identity;
3. compatibility tests for local storage, Git refs, COBs, patches, reviews, and
   bundles;
4. explicit client support for transport-version negotiation;
5. a migration test proving old and new nodes cannot silently mix trust
   domains; and
6. an Idena-only discovery and relay profile that makes no DNS, HTTP, Pkarr,
   seed, or relay request to `radicle.network`;
7. a rebase proving delegate fields and ordinary canonical refs remain unable
   to authorize a merge; and
8. an Idena replay test proving secure Radicle transport cannot change the
   deterministic checkpoint result.

The Idena checkpoints and Idena IPFS content remain authoritative during and
after the upgrade. A future secure Radicle transport can improve discovery and
replication latency; it must not become a privileged merge authority.
